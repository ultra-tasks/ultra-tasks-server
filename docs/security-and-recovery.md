## Real PostgreSQL observations

The local AMD64 Docker drill used PostgreSQL 16, independent authenticated SDK devices, actual encrypted transactions, and separate connections. It exercised migration readiness, signup via isolated SMTP, eight devices, concurrent edits, ciphertext quota refusal, paired backup/restore into another empty volume, nonempty restore refusal, and restart/decryption. The final privacy-document drill enables consent and removes the source public document before restore.

The initial capacity run used eight devices, 100 roughly 1 KiB records per device, ten edit rounds, and additional 16 KiB encrypted records until the 32 MiB current-ciphertext quota refused a batch. Pending intents survived reopening. It measured 359 HTTP requests, 35.0 MB request JSON, 806.8 MB response JSON, 250.6 seconds, 8.0 second p95 request time, 337 MiB peak server memory, and database growth from 9.35 MB to 81.9 MB. These are loopback development observations with concurrent host work, not a user-capacity benchmark.

A separate personal-wakeup sample on the small initial scope delivered ten ordinary edits to eight independently authenticated devices with 214 ms p95/p99 SDK convergence. Its subsequent 800-record concurrent workload took 113.2 seconds, with 7.0 second p95 request time and 129.1 MiB peak server memory. SDK latency excludes application bridge capture, WAN delay, and mobile suspension. CI saves fresh aggregate measurements per architecture. AMD64 completed installation/upgrade acceptance; the ARM64 rerun also verifies that the capacity CLI exits after its assertions rather than waiting on idle network/statistics resources. Its default concurrent workload uses five rounds to leave room for the quota drill within the normal request budget.

**Incremental changes (November 11, 2026).** After its first complete download, an SDK 0.1.4 client receives only heads changed since its cursor. The same real-PostgreSQL drill was run twice on fresh stacks from one AMD64 development image: eight devices, 100 roughly 1 KiB records each, five concurrent rounds, then 16 KiB records until the 32 MiB quota refused a batch. Forcing complete downloads (the previous behavior) measured 358 requests, 672.3 MB response JSON, 269.7 seconds, 6.5 second p95 request time and 322.4 MiB peak server memory. With incremental changes: 360 requests, 90.8 MB response JSON, 56.5 seconds, 0.71 second p95 request time and 231.3 MiB peak server memory. Foreground delivery p95 was 317 ms and 342 ms. Both runs converged and retained pending intents after quota refusal. The first incremental attempt was killed by the container's 768 MiB memory limit because the delta query repeated each manifest per head; the shipped query reads each manifest once.

**Release limitation:** a device's first download, any download after a key update, ownership transfer or restore, and the Android background reminder worker still use complete heads. A long-offline device receives all its changes in one response. Restoring a server backup older than a device's synced state makes that device stop with an error until it reconnects; operators should treat such a restore as a re-download for every native client. Do not promise sub-two-second large-account sync or broad hosted capacity from loopback measurements; representative existing-data beta measurements are still required. After each download the app still rebuilds and validates its whole local dataset; measure that before claiming large-account app latency.

## Optional public calendar publications (0.4.0 client)

Calendar publishing is disabled unless the operator sets `ULTRA_CALENDAR_FEEDS_ENABLED=true`. Apply the calendar-feed database migration before enabling it. The app asks for separate consent for each feed and defaults to busy-only, with optional task titles and times. Notes are excluded. The published ICS is plaintext: the operator and anyone with the URL can read it. This is explicitly outside the encrypted-account guarantee. Update the operator's privacy notice before enabling it.

Feeds belong to an account and cascade on its deletion. Full PostgreSQL dumps include their bodies; backup operators must protect them as readable personal data. There are at most ten feeds per account and 1 MiB per body. Stop or rotate from the app or account dashboard. Rotation/revocation immediately invalidates the old token, including conditional requests, but cannot delete copies a subscriber already downloaded.

Tokens contain 256 random bits, and only SHA-256 hashes persist. Authenticated writes are account-scoped, compare-and-swap revisions prevent old uploads from replacing newer data, and rotation fences queued uploads with a new generation. Public responses require revalidation and carry noindex. App error logs redact feed tokens. Operators must also exclude `/cal/*` from proxy/CDN access and error logs and disable caching on that path. The bundled proxy routes the path to the server; exercise the actual production proxy and an active service worker before release.

Automated acceptance covers real account authentication, SQL, the Angular publishing flow, updates, stable event IDs, URL rotation and revocation. Real Google Calendar, Apple Calendar, Outlook and Thunderbird subscriptions remain a manual release gate. No general encrypted sync schema or existing client contract changes.

## New-device email verification, trusted devices and session lifetime (server beta 2)

Design, limits, failure matrix, compatibility, rollout and rollback are in [account devices and sessions](account-devices-and-sessions.md). Summary of the security claims and their limits:

- **Default-on email check for unrecognized devices.** After a correct password proof, a sign-in from a device with no valid device token needs an eight-digit code sent to the verified address: ten minutes, five attempts across resends, thirty-second resend cooldown, three resends and twelve emails an hour per account (the same bound caps pending challenges at twelve, so none is evicted, and a password change or recovery clears it), single use, stored only as an HMAC. Enrolled TOTP or security keys always take precedence and are never replaced or supplemented by email. It is a second check on a password-only sign-in, **not multi-factor authentication** (NIST SP 800-63B-4 does not accept email as an out-of-band authenticator) and **not phishing resistant**, and it does not protect against control of the mailbox or of a trusted device.
- **Old clients fail clearly.** An application that cannot show the code step gets HTTP 426 `client_update_required` on a new device when the setting applies; it is never let through. `ULTRA_DEVICE_EMAIL_VERIFICATION=false` is the operator kill switch and stops new device tokens too.
- **Trusted devices** use an opaque 256-bit server-issued token stored as a SHA-256 digest. It never authenticates alone, is bound to one account, follows use (it lapses after the session idle window without activity) and is removed individually (the record is deleted, and removing a device other than the one in use needs a recent sign-in and, with a second factor enrolled, an MFA code), on password change (all but the current device), on recovery (all) and when the setting is turned back on (all but the current device). Device records hold a sanitized display name and timestamps, never an IP address or user agent. Browser-to-app approval must come from a session on a still-trusted device.
- **Sessions slide.** A refresh renews an idle window (`ULTRA_SESSION_IDLE_DAYS`, default 180) up to an absolute cap fixed at sign-in (`ULTRA_SESSION_MAX_DAYS`, default 1095, `0` for none). Single-use refresh rotation and reuse revocation are unchanged, with no leeway window; recent-sign-in (ten minutes) requirements for security changes are never renewed by refresh. At most thirty sessions are live; at the cap an unused session is retired when a new sign-in is actually issued. A refresh token names its own session and generation and carries a MAC, so nothing is stored per refresh: a forged token reads and writes nothing, and a replay of any earlier generation revokes the session however many rotations ago it was issued. Revoked sessions are deleted 30 days after their last activity and the sessions list shows at most 100 rows.
- **Known limitation:** if the response to a refresh is lost, the retry presents a consumed token and the session is revoked; clients must show a reconnect state. An idempotent retry bound to a client secret is a possible follow-up that needs its own security review and is not implemented.

Automated evidence is PGlite-backed route and SQL tests using the real SDK (see the verification section of the linked document). Real PostgreSQL concurrency, the real-PostgreSQL refresh integration suite and published-image upgrade acceptance were not run in this work and stay release gates, as does independent security review.
