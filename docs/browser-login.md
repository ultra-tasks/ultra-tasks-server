# Browser-to-app account login, version 1

This additive flow supports the same account origin and Docker installation for official and self-hosted servers. It does not use a central callback relay. Existing OPAQUE, MFA, vault, direct login, and sync formats remain compatible. Passwords are entered only into the selected server's account website; browser-delivered code remains part of the account website's existing trust boundary.

Before opening a browser, the app generates a 256-bit state, a 256-bit redeem verifier and its SHA-256 challenge, and an ephemeral P-256 recipient key. `/browser-login/start` records a five-minute request bound to the installation UUID, canonical server URL, exact return URI, state, public key, challenge, device label, and optional account identifier. The initiating device persists the pending verifier/private key in device-protected storage before navigation. The request ticket and a full request fingerprint are carried to the website; the fingerprint is in the fragment, not sent in HTTP requests. The website checks it before presenting approval.

Approved return targets are exactly `ultratasks://account-login` (desktop), `app.ultratasks://account-login` (Android/iOS), and `urn:ultra-tasks:web` (polling-only browser client). Arbitrary redirects are rejected. The existing native URL router and Electron protocol queue own delivery, including cold launch. A callback contains only `result=<ticket>&state=<state>`; it never chooses a server or installs a session by itself.

The website completes OPAQUE password authentication, verified email, and enrolled MFA through the existing account flow. It shows the account, selected server, requesting device, and a matching request code, then requires explicit approval. A recent live browser session is required. The SDK encrypts the 32-byte vault master key to the request's ephemeral public key using the existing RFC 9180 P-256/HKDF-SHA256/AES-256-GCM HPKE suite. HPKE info and AAD use the existing grant encoding with `serverId`, `recipientId=accountId`, `epoch=1`, and `scopeId=canonical({purpose:'browser-login-v1', request, vaultVersion, bundleHash})`. The account signing key signs `{action:'browser-login-v1', request, accountId, vaultVersion, bundleHash, grant}`. `bundleHash` is SHA-256 of the canonical encrypted account bundle. No plaintext vault key reaches the server.

The server verifies the signature and account hint under account/session/request locks. It stores only the encrypted grant, signature, approving session ID, and binding. Redemption requires the original verifier, ticket, state, installation identity, and an unexpired request. The approving browser session must still be live and the encrypted bundle hash/version unchanged. The server atomically deletes the request and creates a separate device session through the existing native or Better Auth session issuer. Replay fails. A lost redemption response requires a new sign-in; an issued session is visible in Devices for revocation.

The SDK checks the complete request, signature, server/account identity, optional identifier, bundle hash/version, and HPKE context before opening the vault with the received master key. The existing vault/public-key checks still apply. A callback with no matching local pending attempt is ignored. Polling uses the identical device proof and redemption path, so a blocked return link cannot weaken approval. Cancellation deletes the pending request using the device proof and clears protected local material. Browser denial also removes the pending request. Expiry, account deletion, bundle changes, or approving-session revocation invalidate an outstanding grant. One pending request per local app profile avoids callback/account switching races.

Security acceptance includes both session engines; MFA before approval; second independent server origin; wrong verifier/state/recipient/server/account/binding/signature; expired, denied, canceled and replayed requests; password/recovery changes and session revocation; callback cold/warm routing; protected-storage failures; cancellation while polling; and real website/app paths. Platform wiring and automated tests do not replace physical-device and packaged Windows/macOS/Linux release acceptance.

This uses the external-browser and proof-of-possession principles of [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html), with the project's existing [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html) HPKE suite. It is a custom OPAQUE/E2EE flow, not an OAuth implementation.

The fresh-context review fixed cleanup of a newly issued device session when local app finalization fails. The app retains the issued proof until setup completes and can revoke the failed session even if the local SDK was locked during cleanup. No unresolved protocol finding remained. Local acceptance passed 18 SDK tests, 62 native tests (including 14 handoff cases), focused app controller/callback/storage checks, and real Windows Electron warm/cold return. Website MFA and blocked-return polling passed on two independent server origins. Real PostgreSQL concurrent-redemption cases are included in the existing CI database job. Physical Android/iOS/macOS acceptance remains a release gate; automated tests and this review are not a specialist cryptographic audit.
