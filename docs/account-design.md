# Account website design

The account website extends the Ultra Tasks app's design language. It uses the same system font stack, 4/8px spacing scale, six type roles, 10px control/card corners, flat bordered surfaces, one filled accent button per surface, and default teal accent. `apps/account/public/account-theme.css` snapshots the app's normalized default palette from client commit `b79c0f94d5`, including accessible text, border, focus, and selected-state roles, plus the normalizer's default warning and success tones (used only for message borders and icons, never for text). Update both modes when those defaults change. The logo is copied from the client's `src/assets/ultra-tasks/logo.svg`; it retains the project's existing license.

The website follows the operating system's light/dark preference. The app's account screen inherits the app's active theme, including user customizations, and uses its shared Material controls. The website has no font CDN, tracking, or new UI framework dependency. The production policy is `style-src 'self'` and `default-src 'self'`: pages carry no `style` attributes or `<style>` blocks, icons are an inline SVG sprite in the page (no `data:` images), and the browser test serves the page with that exact policy.

## One flow

The maintainer's report was that login, dashboard and in-app sign-in feel disjointed. The website therefore uses one noun, **Ultra Tasks account**, one vocabulary, and one place for messages.

**Sign in** is the first view. It has a single heading, "Sign in to your Ultra Tasks account", then Email, Password (with a show/hide button that toggles the same input, so password managers, autofill and paste keep working), a primary **Sign in**, "Forgot password?" under the password and a clearly visible **Create account** button. Nothing else is asked. The device name is derived from the browser and operating system ("Firefox on Windows") and is only a label in the device list; it is never used as trust evidence. It can be edited under **Advanced**, which also holds "Unlock cached account offline" (shown only when this browser holds an encrypted cache). "Resend verification email" and "Enter a verification code" appear only after a "Verify your email" error. The email field accepts a legacy username (older accounts keep signing in) but is labelled Email and the page never promotes usernames.

**Create account** is three announced steps (Account, Recovery key, Verify email; `aria-current="step"`). Step 1 asks for email, password, confirmation and, when the operator requires it, the privacy/terms consent: no username and no display name. Step 2 explains why the recovery key matters, keeps copy/save/print, the data-loss warning and the explicit "I saved my recovery key" confirmation, and **Back to account details** still discards the prepared key. Step 3 explains the 8-digit code, its 30-minute registration expiry and that a new code does not extend it, and keeps "Send a new code".

**Verify this device** appears after a correct password when the server needs an email check for a device it does not recognize. It names the masked address, takes an 8-digit one-time code (`inputmode="numeric"`, `autocomplete="one-time-code"`), shows the server's resend cooldown as a countdown, reports wrong, expired and exhausted codes in place, and offers "Back to sign in". A device token is always kept after a successful sign-in: the one the server newly issued (it does so only for a device it did not recognize) or, when it issued none, the valid one this browser already presented; an existing stored token is otherwise left alone. It lives in `localStorage` under a key derived from the server origin and a hash of the email (a convenience for this browser only: it never authenticates by itself) and is sent on later sign-ins. There is no choice to make: the page says that the browser is remembered and that Devices can remove it. A server that answers HTTP 426 `client_update_required` produces a message and a reload action, never a bypass. An enrolled authenticator or security key always takes precedence: the MFA step replaces the email step.

**Messages** live with the thing they describe. Each form, panel and step has two always-present live regions (polite `status`, assertive `alert`) and messages are inserted into them as inline notices with an icon and a tone; there is no floating global status line. A visually hidden polite region announces transitions that have no visible message (signed in, devices refreshed). The primary button of a running action shows a busy label and a spinner and stays focusable (it is not disabled), and only one action runs at a time. Failures are classified into calm sentences (wrong credentials, unverified email, recent sign-in required with a **Sign in again** action, network, rate limit, update required) and the server's stable error codes get their own wording on the card where they happen: `session_limit` ("This account has too many signed-in devices. Sign in on a device you already use and remove an old one in Devices."), `verification_rate_limited`, `email_delivery_failed`, `resend_too_soon` and `resend_limit`, and `device_verification_required` when an approval is refused because this browser has not finished the new-device check (it offers **Sign in again**, and the app request is still waiting afterwards). A refusal that ends the pending sign-in (a lost challenge, or mail that could not be sent when asking for a new code) returns to the sign-in card with the reason.

**Approving a sign-in started in the app** keeps the same wording as the app: a banner shows the app's device name, server and request code above the sign-in and MFA steps, the approval step repeats the code and device ("Connect your app"), and the finish step offers **Open Ultra Tasks**. A session that passed MFA, the email check or a trusted device satisfies the new device too; nothing extra is asked.

## Dashboard

The header names the product ("Ultra Tasks account") and the signed-in email, with **Lock** and **Sign out** grouped. Lock clears the encryption keys and tokens from the page and returns to sign-in; the server session stays and appears in Devices. Sign out additionally ends this browser's session on the server. Each button carries its explanation in `title` and `aria-describedby`. The navigation has three areas and becomes a row on phones.

- **Account**: email (with **Change email**, an email-only form that sends a verification link and sends the address alone to the server; it needs a sign-in from the last ten minutes), **Account ID** (the immutable account UUID: read-only monospace, a Copy button with a polite confirmation, and "Share this ID with support. It is not a password and does not prove you own the account."), the server address, a quiet storage summary in friendly words (no meter until something is stored), the **Get Ultra Tasks** link, and, only when the server offers calendar publication, a **Published calendars** section that keeps the plaintext-disclosure text and the rotate/stop controls.
- **Security**: a **Sign-in protection** group explains new-device email verification (a switch, shown only when the server offers the feature and reports the setting; turning it off shows a warning and asks for a second-factor code when one is enrolled) and two-factor authentication (state, enrolled methods, set up, add, remove, and the recovery-code note). **Change password** is a collapsed section. **Delete account** sits in a separate danger zone with the full warning and the typed-email plus checkbox confirmation, collapsed behind a disclosure.
- **Devices**: trusted devices and other sessions with name, "This device" badge, trusted marker, when they were added and last active, and **Remove device** after an inline confirmation (a small form; the safe choice has focus). Removing this browser's own device needs nothing more and signs it out. Removing another trusted device is a security change: it needs a sign-in from the last ten minutes and, when an authenticator or security key is enrolled, a current **Authenticator or recovery code** typed into that same inline form (an account with security keys only is told "Use a recovery code to remove another device.", because the server accepts only an authenticator or recovery code here). A wrong code says "That code did not work." and keeps the session; a stale sign-in says to sign in again, before the code is used up, and **Sign in again** returns to the sign-in card with "Sign in again to remove devices."; with no second factor enrolled the confirmation alone is enough, and a refusal then can only mean the session has ended. Removed sessions are listed collapsed; an empty list says so.

If the session ends elsewhere, the next request reports "Your session ended" on the sign-in card instead of leaving a blank page; secrets and personal values are cleared from the page whenever it locks.

## Source layout

`apps/account/public/ultra-account.html` and `ultra-account.css` are the page and its styles; `apps/account/src/portal.ts` wires the flows and imports small modules: `ui.ts` (lookups, notices, busy buttons), `dashboard.ts` (pure rendering of storage, factors, devices and calendars), `device.ts` (device label and token storage), `errors.ts`, `format.ts`, `profiles.ts` (the encrypted offline-unlock cache) and `clipboard.ts`. tsup bundles them into the single portal script. `scripts/install-dashboard.mjs` installs the theme, logo, and portal into both the inherited public directory and the private-only account directory used by the production image. Run `npm run quiet -- build:dashboard` after editing account assets; never edit the installed copies.

## Testing

Browser coverage (`npm run test:accounts:browser`) exercises real registration without username or display name, recovery-key export and discard, the saved-key and consent safeguards, verification by code and by link, security-key enrollment and login, password recovery, offline unlocking, device approval, confirmed deletion, the Account ID copy, devices with confirmed removal, email change, the lost-session and recent-sign-in messages, keyboard-only sign-in, a 390px layout without horizontal scroll in light and dark, a page with no inline styles under the production policy, and the whole new-device flow (verification, cooldown and resend, remembering, 426, session-limit, email-limit and mail-failure messages, every refused new code, the switch, approving an app sign-in afterwards, a refused approval that is retried after signing in again, and removing devices with and without a second factor, with a wrong code, a stale sign-in and a security-keys-only account). The Better Auth browser suite and the website-to-app suite cover the same pages with MFA and the app handoff; they can also capture the real Windows Electron app using `ULTRA_ELECTRON_EXECUTABLE` and `ULTRA_ELECTRON_APP`, with `ULTRA_CLIENT_DIST` pointing to a current independent app build and `ULTRA_AUTH_SCREENSHOTS` pointing to an output directory. Test accounts and app profiles are isolated from personal data.

These are local UI acceptance results, not a hosted deployment or a cryptographic audit. Computed text contrast was checked against WCAG AA for every view in both themes; no assistive-technology (screen reader) run was made.
